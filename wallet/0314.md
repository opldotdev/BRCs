# BRC-314: Native Application Wallet Communications Substrate

Open Protocol Labs (info@opl.dev)

**Authors:** Luke Rohenaz (luke@opl.dev)

## Abstract

This document specifies a fourth communications substrate for the [BRC-100](./0100.md) wallet interface, for the case where the application and the wallet are **separate natively installed applications on the same mobile device**. The three existing substrates — [BRC-5](./0005.md) localhost HTTP, [BRC-6](./0006.md) cross-document messaging, [BRC-7](./0007.md) window object — all assume a shared browser process, a shared origin model, or a loopback socket. A native application has none of these.

The substrate carries a request from an application to a wallet, and a result back, as **domain-verified deep links in both directions**. The payload rides in the URL fragment, which no HTTP server ever receives. The result is signed with [BRC-77](../peer-to-peer/0077.md) and names a [BRC-95](../transactions/0095.md) Atomic BEEF resource, so the calling application performs its own SPV rather than trusting the wallet's answer.

Because the operating system provides no call-and-return primitive, this document also specifies what an implementation must do when the return leg never arrives, which is the failure the other three substrates never have to consider.

## Motivation

[BRC-6](./0006.md) states its own motivation as extending wallet communication beyond the assumptions of the substrate before it. The same gap has reappeared one layer down.

On a mobile operating system there is no shared window, no shared document, and no loopback port an application may rely on. Two installed applications communicate only through the mechanisms the operating system sanctions for that purpose: a URL handed to the system, and the system deciding which application receives it. There is no return value. The caller is suspended, and may be terminated, while the callee runs.

Three properties follow, and they are what this document exists to specify:

1. **Identity is the verified domain, not a claim.** A custom URL scheme may be registered by any installed application, so it can never identify anybody. A deep link bound to a domain the operating system has verified against the publisher can. [BRC-151](../opinions/0151.md) states the general rule — *"The wallet must not trust a domain value merely because an application supplied it"* — and on this substrate the verified domain is the only field that satisfies it.

2. **A callback is a hint, never proof.** The operating system does not guarantee delivery of the return leg. A design in which the callback is the only channel produces applications that show a receipt for a payment that never happened, or lose a payment that did.

3. **The wallet is discovered, not assumed.** A browser extension is present or absent within one process. A native wallet must be findable by an application that has never met it, and an application must be identifiable by a wallet that has never met it.

## Specification

### 1. Terminology

| Term | Meaning |
|---|---|
| **Application** | The native application making a request. Called the *originator* in [BRC-100](./0100.md). |
| **Wallet** | The native application holding keys and answering requests. |
| **Verified domain** | A domain that the operating system has cryptographically associated with an installed application before delivering it a link. |
| **Callback** | The application's verified `https` URL, to which the wallet returns a result. |
| **Session** | A `sessionID` and a monotonically increasing `seq`, together naming one request. |

The key words MUST, MUST NOT, REQUIRED, SHALL, SHOULD, SHOULD NOT, MAY, and OPTIONAL are to be interpreted as described in RFC 2119.

### 2. Transport

Both legs are `https` links bound to a verified domain.

```
Request   https://<wallet-domain>/brc100/<action>#<base64url(payload)>
Result    https://<app-domain>/<app-path>#<base64url(payload)>
```

The payload MUST travel in the **fragment**. A fragment is never transmitted to an HTTP server, so neither a payment request nor a signed result reaches the domain's operator even though the link names their domain. A wallet MUST NOT accept a payload from the query string or path.

An implementation MUST reject a request whose scheme is not `https`. A custom URL scheme MAY be accepted in development builds only, and MUST NOT be the specified transport, because a scheme may be claimed by any installed application and the operating system offers no chooser when several do.

If no application claims the wallet domain, the operating system opens it in a browser. The wallet's operator SHOULD serve a page at that path which reads the fragment client-side, explains what the user attempted, and offers to install the wallet. This is a property worth preserving deliberately: the not-installed case degrades to an explanation rather than an error.

#### 2.1 Actions

| Path | Payload | Meaning |
|---|---|---|
| `/brc100/pay` | §3 request | Ask the wallet to make a payment |
| `/brc100/result` | §5 replay | Ask the wallet to re-send a result it already produced |

A wallet MUST match the action path exactly. It MUST NOT treat an unrecognised path as any known action, and MUST NOT match on a suffix.

### 3. Request

```
{
  "v":            1,
  "method":       "pay",
  "appName":      "Frenly",
  "recipientKey": "03a1…9f2c",
  "recipientName":"Kurt Wuckert Jr.",
  "satoshis":     120000,
  "memo":         "Coffee",
  "reference":    "9f2c41a7b0e3",
  "callback":     "https://frenly.chat/brc100/return",
  "sessionID":    "frenly-8c1a2b3d",
  "seq":          1
}
```

| Field | Required | Notes |
|---|---|---|
| `v` | yes | Substrate version. A wallet MUST refuse a version it does not implement. |
| `method` | yes | The BRC-100 operation requested. |
| `appName` | yes | **Decoration only.** See §4. |
| `recipientKey` | yes | Compressed secp256k1 public key, 33 bytes hex. |
| `satoshis` | yes | MUST be greater than zero. |
| `reference` | yes | Application-generated random value, embedded in the payment. See §6. |
| `callback` | yes | MUST be `https` and MUST have a host. |
| `sessionID`, `seq` | yes | Together identify this request. |

A wallet MUST refuse a request that fails any of these constraints. It MUST refuse rather than repair: a request with a zero amount, an invalid recipient key, or an empty reference is not a request to be interpreted generously.

### 4. Identity — what the user is shown

`appName` is supplied by the caller and verified by nobody. A wallet MUST NOT present it as the identity of the requesting application.

The host of `callback` is the only identity the operating system has verified, because delivery of the return leg to that application depended on that verification. A wallet MUST show that host as the requesting party's identity, and MUST present `appName`, if shown at all, as a subordinate claim.

#### 4.1 Application metadata

A wallet SHOULD obtain the application's display name and artwork from the manifest specified in [BRC-116 §3.2](./0116.md) — a [W3C Web App Manifest](https://www.w3.org/TR/appmanifest/) served at `https://{domain}/manifest.json` — resolved against the **verified callback host**, never against a URL supplied in the request. An icon URL carried in a request would let any caller display any brand's artwork beside a live payment prompt.

The `icons` member's `purpose` distinguishes the two assets a wallet needs, and an implementation SHOULD honour that distinction:

| `purpose` | Wallet usage |
|---|---|
| `monochrome` | Tinted by the wallet, for list rows and activity lines |
| `any` | Rendered as authored, for a consent prompt |
| `maskable` | Where the wallet clips artwork to its own shape |

A wallet MUST ignore any manifest asset that is not same-origin with the verified callback host.

A wallet SHOULD fetch a manifest at most once per host and cache the result. Fetching per request discloses to that host that a particular user is transacting, from a particular address, at a particular moment — the metadata exposure [BRC-151 §4](../opinions/0151.md) describes.

Where no manifest is available, a wallet MUST NOT substitute artwork of its own choosing that could be mistaken for the application's. It SHOULD show a visibly generic placeholder alongside the verified host.

#### 4.2 Wallet discovery

A wallet's operator SHOULD serve a discovery document at `https://{domain}/.well-known/brc100-wallet.json` so that an application may construct a request without hard-coding one wallet:

```
{
  "name":        "1Sat Wallet",
  "icon":        "https://www.1sat.app/icon-512.png",
  "sessionBase": "https://www.1sat.app/brc100",
  "platforms":   ["ios", "macos"],
  "methods":     ["createAction", "internalizeAction", "getPublicKey", …]
}
```

`methods` names the BRC-100 methods the wallet answers on this substrate. Every URL in the document MUST be the operator's canonical host. A document that names a host which redirects will fail against any client that does not follow redirects, and clients are not required to.

An application MUST NOT treat the presence of this document as evidence that the wallet is installed. Installation is discovered only by the operating system's response to the link.

### 5. Result

```
{
  "v":                 1,
  "sessionID":         "frenly-8c1a2b3d",
  "seq":               1,
  "txid":              "6a1f…",
  "reference":         "9f2c41a7b0e3",
  "error":             null,
  "signature":         "QkIzAQ…",
  "walletIdentityKey": "02de…",
  "callbackHost":      "frenly.chat",
  "beefURL":           "https://…/beef/6a1f…"
}
```

`error`, when present, MUST be one of:

`user_cancelled`, `permission_denied`, `insufficient_funds`, `session_expired`, `limit_exceeded`, `unknown_method`, `malformed_request`, `untrusted_callback`, `wallet_busy`, `unknown_result`.

#### 5.1 Signature

`signature` is a [BRC-77](../peer-to-peer/0077.md) packet, base64. BRC-77 rather than Bitcoin Signed Message: BRC-77 derives a per-message child key under [BRC-42](../key-derivation/0042.md)/[BRC-43](../key-derivation/0043.md), so signatures neither reuse the identity key nor link to one another.

The signed bytes are the UTF-8 encoding of these fields joined by `\n`, in this exact order:

```
brc100.result.v<v>
<sessionID>
<seq>
<txid>
<reference>
<error>
<callbackHost>
<beefURL>
```

An absent field is the empty string. JSON MUST NOT be used as the signing input, because key ordering is not guaranteed across encoders and two correct implementations could then disagree about what was signed.

`beefURL` is covered by the signature, so a hostile relay cannot redirect the caller to a transaction other than the one signed for.

#### 5.2 Result binding

`callbackHost` MUST record the host of the callback that produced the result. §7 requires it.

#### 5.3 SPV, not assertion

`beefURL` SHOULD name a resource serving [BRC-95](../transactions/0095.md) Atomic BEEF for `txid`. The application SHOULD retrieve it and validate against block headers it already tracks.

A link is carried rather than the bytes because BEEF grows with the input history it carries, while the return leg is a URL of bounded length. This weakens nothing: BEEF is self-verifying, so a hostile host may fail to serve it but cannot forge it. Content-addressed retrieval — [BRC-26](../overlays/0026.md) UHRP — makes that property explicit rather than incidental.

### 6. Three layers of truth

An implementation MUST distinguish these, and MUST NOT present a lower layer as a higher one:

| Layer | Source | Status |
|---|---|---|
| 1 | The returned callback | A **hint**. May never arrive. |
| 2 | A replayed result (§7) | The wallet's durable record of its own answer. |
| 3 | `reference` located on chain | **Authoritative.** Requires no cooperation from the wallet. |

An application MUST NOT describe a payment as settled on the strength of layer 1 alone. `reference` exists so that layer 3 is reachable without the wallet's participation, including after the wallet is uninstalled.

### 7. Replay, and the callback that never arrives

The operating system may terminate either application at any point, and does not guarantee that the return leg is delivered. An application that received no result MAY ask for it again by opening `/brc100/result` with:

```
{ "v": 1, "sessionID": "…", "seq": 1, "callback": "https://frenly.chat/brc100/return" }
```

A wallet:

- MUST persist every result it produces, keyed by `sessionID` and `seq`, because the case a replay exists for is precisely the case in which the wallet was terminated.
- MUST refuse a replay whose callback host differs from the `callbackHost` recorded on the stored result, returning `unknown_result`. Without this binding, any installed application could obtain another application's txid, reference and signature by guessing a session identifier.
- MUST return the identical stored result. A given `sessionID` and `seq` has exactly one answer for all time, and a user's refusal is as final as their approval.
- MUST answer `unknown_result` for a session it has no record of, and MUST NOT treat a replay as a new request.

A wallet MUST refuse a second request while one awaits the user, returning `wallet_busy`. Replacing a consent prompt under a user who is deciding is worse than making the second caller retry.

### 8. Security considerations

**Custom schemes cannot carry either leg.** Any installed application may register any scheme, and the operating system chooses among claimants without asking. A generic scheme such as `bsv:` is a guaranteed collision rather than an accidental one.

**The fragment is a privacy boundary, not a security one.** It keeps payloads away from the domain's server. It does not authenticate them. Every constraint in §3 and §4 still applies.

**Result binding is not optional.** See §7.

**A refusal is a result.** A wallet SHOULD return an error result rather than nothing, so the application learns the outcome instead of waiting. Where the callback itself is untrustworthy — not `https`, or without a host — the wallet MUST NOT open it, and MUST report the failure to its own user instead.

**Metadata.** Every request tells the wallet which application the user is transacting with, and §4.1 fetching would tell that application when. [BRC-151](../opinions/0151.md) should be read in full by implementers.

## Implementation

An open implementation of both sides exists: 1Sat Wallet (the wallet) and Frenly (the application), both native Swift for iOS, using domain-verified Universal Links in both directions and the BRC-77 result signature described in §5.1.
