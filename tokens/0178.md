# BRC-178: Collaborative Atomic Exchange for BRC-100 Wallets

Open Protocol Labs ([info@opl.dev](mailto:info@opl.dev))

## Abstract

This document defines how two BRC-100 wallets collaboratively construct,
review, and sign one Bitcoin transaction that exchanges BSV, 1Sat Ordinal
NFTs, or BSV-21 fungible tokens.

The parties first agree on trade terms, then resolve those terms to concrete
inputs and receiver-controlled outputs. One wallet constructs and funds a
final candidate transaction. Each party independently verifies that candidate
and signs only the inputs it owns with `SIGHASH_ALL | SIGHASH_FORKID`. The
transaction moves every agreed asset or none of them.

Bitcoin transaction signatures authorize the spends. This profile does not
require a separately signed offer or application-level commitment, and it
does not prescribe a coordinator or transport protocol.

## Motivation

[BRC-79](./0079.md) describes a token exchange in which one party first uses
`SIGHASH_SINGLE` and the other completes the transaction with
`SIGHASH_ALL`. That construction remains valid.

Current BRC-100 wallets can instead wait until every concrete input, output,
fee, and change output is fixed, then have both parties review the final funded
transaction and use `SIGHASH_ALL | SIGHASH_FORKID`. This profile specifies
the construction and verification requirements for 1Sat Ordinals and BSV-21.

## Scope

Version 1:

- has exactly two parties;
- settles every exchange leg in one Bitcoin transaction;
- uses one BRC-100 wallet as the transaction builder and mining-fee payer;
- supports ordinary BSV, 1Sat Ordinal NFTs, and BSV-21 value outputs;
- permits ordinary BSV to be contributed by the builder only;
- requires each party to validate all asset inputs and sign only its own; and
- uses existing BRC-100, 1Sat, and BSV-21 mechanisms.

This profile does not define presence, discovery, chat, order books, offer
storage, reservations, user interface, or a relay service. It does not define
a new token, overlay, script template, basket, wallet method, or message
format.

## Relationship to BRC-79

BRC-79 and this profile use different signing sequences.

BRC-79 permits the accepting party to commit to one output first with
`SIGHASH_SINGLE` while all transaction inputs are already fixed. Historical
1Sat marketplace flows also use `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` when a
seller must sign before a buyer adds funding inputs and outputs. In this
profile, no input is signed until the builder has produced the final funded
transaction, and every contributed input uses
`SIGHASH_ALL | SIGHASH_FORKID`.

Implementations MUST NOT combine signatures from the two profiles.

## Terminology

- **Builder**: The party whose BRC-100 wallet constructs and funds the
  candidate transaction.
- **Terms confirmation**: A user-interface decision to accept the proposed
  trade. It is not a Bitcoin signature and does not freeze a transaction.
- **Contribution**: The concrete asset outpoints, receiver-controlled output
  scripts, token change, and fresh validation evidence supplied by one party.
- **Candidate transaction**: The complete transaction structure after the
  builder wallet has added funding inputs and change, but before all unlocking
  scripts are present.
- **Asset input**: A 1Sat Ordinal or BSV-21 input contributed by either party.
- **Receipt output**: An output controlled by the party receiving an asset.

The key words `MUST`, `MUST NOT`, `SHOULD`, `SHOULD NOT`, `RECOMMENDED`, and
`MAY` express normative requirements when written in uppercase.

## Negotiation

The parties may revise proposed trade terms until both confirm them. Terms may
name an ordinal outpoint, a BSV-21 token ID and quantity, or an ordinary BSV
amount. Terms confirmation does not require concrete BSV funding inputs and
does not authorize a spend.

After terms confirmation, each wallet resolves its side to a contribution.
For BSV-21 this includes the selected current transfer tips, exact change, and
fresh overlay policy. For an ordinal this includes its current tip and the
evidence needed to validate it. Every receiver supplies or approves its own
destination scripts.

If one side contributes ordinary BSV, that side MUST be the builder because
its BRC-100 wallet selects and signs the ordinary funding inputs and creates
its change. Otherwise, the application MAY select the builder using any
deterministic rule agreed by both parties. Both complete contributions are
required before construction, regardless of how the builder is selected.

This profile does not prescribe a negotiation payload. A live application
SHOULD use a mutually authenticated channel such as BRC-103. An application
that persists messages in an untrusted relay MAY protect those messages with
BRC-77. Message authentication lets the recipient verify the sender and detect
tampering. It does not authorize a Bitcoin spend.

Parties MUST NOT sign Bitcoin inputs during negotiation or contribution
resolution. A change to the agreed terms or contributions requires renewed
confirmation before construction. A change to any signature-committed field of
the candidate requires both parties to review the new candidate and replace
all signatures already produced.

## Transaction construction

The builder MUST possess both complete contributions before asking its wallet
to construct the transaction. It MUST NOT substitute display metadata for a
concrete outpoint, locking script, token quantity, or source proof.

The builder asks its BRC-100 wallet to create the candidate transaction with:

```json
{
  "options": {
    "signAndProcess": false,
    "randomizeOutputs": false
  }
}
```

Asset source transactions and proofs are supplied through `inputBEEF`.
Inputs that will be signed later use the BRC-100
`unlockingScriptLength` mechanism. The builder wallet MAY add ordinary
funding inputs and change. If the terms contain an ordinary BSV leg, the
corresponding payment output is included in this same call; a non-builder never
appends ordinary BSV inputs after this point.

The builder sends the resulting candidate transaction and the source data
needed to validate it to the other party. Atomic BEEF is the RECOMMENDED BSV
container. BIP-174 PSBT is not required: a partially signed transaction format
can transport metadata and signatures, but it does not change which transaction
fields a signature commits to.

The BRC-100 action reference returned to the builder is a capability for
completing the retained wallet action. It MUST NOT be sent to the other party
or a relay. If construction ends before completion, the builder SHOULD call
`abortAction`.

## Required review

Before signing, each party MUST reconstruct the candidate transaction and
verify:

1. every asset input it agreed to contribute appears exactly once;
2. it is not being asked to sign any other input;
3. every expected receipt output has the approved script, satoshi value, asset
   identity, and asset quantity;
4. every change output belonging to it is correct;
5. ordinary BSV payments, mining fees, and overlay fees are separately
   acceptable;
6. every input is current, unspent, and valid under its asset profile; and
7. transaction version, outpoints, input sequences, output order, output
   scripts, output satoshis, and lock time are acceptable.

The candidate transaction is authoritative. Display metadata, a relay record,
an offer identifier, and pre-build input or output indexes MUST NOT override
what the wallet derives from the transaction. A review manifest or equivalent
local record MUST bind every field listed above, including version, lock time,
and every input sequence. Signing MUST fail if the candidate differs from
that reviewed record in any signature-committed field.

## 1Sat Ordinal NFT requirements

A 1Sat Ordinal input is identified by its current tip outpoint, not its image,
name, metadata, or claimed origin.

Before signing, both parties MUST verify that:

1. the tip is unspent and controlled by the contributing wallet;
2. the source output contains exactly one satoshi;
3. the tip-to-origin relationship is valid under BRC-159, preferably with a
   BRC-150 remittance; and
4. transaction satoshi ordering moves that exact satoshi into the approved
   one-satoshi receipt output.

The receipt output and remittance MUST follow the BRC-147 `1sat` basket
profile. Implementations MUST trace the final candidate transaction and MUST
NOT assume the builder preserved requested input or output indexes.

## BSV-21 requirements

A BSV-21 transfer is identified by its BRC-161 or BRC-162 token ID and an
unsigned 64-bit atomic amount. A symbol, icon, decimal precision, or display
name is not an asset identifier.

Before signing, both parties MUST establish that every selected token input:

1. is an unspent transfer output for the exact token ID;
2. is valid under BRC-161 or BRC-162;
3. has sufficient lineage evidence under BRC-176 or an equivalently verified
   live overlay response; and
4. uses a supported owner-controlled locking script.

For each token ID, the candidate transaction MUST satisfy:

```text
sum(valid selected value inputs)
  = sum(receiver value outputs) + sum(owner change outputs)
```

Change is mandatory when selected inputs exceed the transferred amount.
Deploy, mint, authority, burn, and implicit-burn constructions are forbidden.
Amounts from different token IDs MUST NOT be combined.

Receipt and change outputs MUST follow the BRC-163 `bsv21` basket profile.
Any overlay admission fee MUST be resolved and included in the candidate
transaction before either party signs.

## Signing and assembly

Each party signs exactly the inputs it owns against the final candidate
transaction. Every contributed asset input MUST use:

```text
SIGHASH_ALL | SIGHASH_FORKID = 0x41
```

This signature preimage commits to the transaction version, lock time, all
input outpoints and sequences, all outputs, and the source amount and script
for the input being signed. Other inputs' unlocking scripts are not part of
that preimage, so the parties can produce their signatures independently for
the same candidate transaction. `SIGHASH_ANYONECANPAY` is unnecessary and
forbidden because no party signs before all inputs are fixed.

Each wallet MUST locally verify every unlocking script it creates against the
source output before releasing it. The party returns its unlocking scripts, or
an equivalent partially signed transaction, to the builder.

The builder MUST verify every received unlocking script against the unchanged
candidate transaction and MUST reject any asset-input signature whose sighash
byte is not exactly `0x41`. Successful script execution alone does not establish
compliance with this signature policy. The builder then supplies the scripts
to BRC-100 `signAction` for the retained action reference. `signAction` signs the builder wallet's
ordinary funding inputs and returns or broadcasts the completed transaction.
A builder that contributes only ordinary BSV has no separate asset-input
authorization to return; its spend authorization occurs when its wallet
reviews and completes `signAction`.

If any outpoint, sequence, output, script, satoshi amount, fee, version, or lock
time changes, the changed candidate MUST be reviewed and signed again.
Implementations MUST NOT transplant signatures onto a different candidate.

An implementation that needs one party to sign before the other party's inputs
or outputs are fixed is outside this profile. It SHOULD use BRC-79 or another
profile that explicitly defines the required `SIGHASH_SINGLE` and
`SIGHASH_ANYONECANPAY` commitments rather than mixing them into this flow.

## Broadcast and receipt handling

Retries SHOULD submit the same completed transaction bytes. Applications MUST NOT
report a submission attempt or timeout as confirmed settlement.

For BSV-21, settlement requires both Bitcoin transaction acceptance and the
required overlay admission. Bitcoin acceptance does not by itself establish
overlay admission, and an overlay failure does not reverse an accepted Bitcoin
transaction. If the broadcast outcome is uncertain, an application SHOULD
query the expected transaction and contributed outpoints before constructing
a replacement.

After acceptance, each receiving wallet SHOULD call BRC-100
`internalizeAction`:

- 1Sat Ordinal NFTs use BRC-147 remittance into `1sat`;
- BSV-21 uses BRC-163 remittance into `bsv21`; and
- ordinary BSV uses the applicable BRC-100 payment remittance.

Internalization MUST be idempotent. A local internalization failure does not
reverse an accepted Bitcoin transaction.

## Security considerations

- **Atomicity**: All exchange legs occur in one transaction.
- **Transaction substitution**: `SIGHASH_ALL | SIGHASH_FORKID` prevents a
  relay or counterparty from changing inputs or outputs after signing.
- **No second authorization object**: A signed offer or JSON object is not a
  substitute for wallet review and is not required for transaction safety.
- **Coordinator compromise**: A relay can delay, omit, duplicate, or reorder
  messages, but it cannot alter the signed transaction.
- **Stale inputs**: Recheck immediately before signing. A double spend can make
  the whole transaction invalid but cannot settle only one exchange leg.
- **Signature release**: Once a valid unlocking script is shared, a user
  cannot revoke it. An application-level expiry can stop further cooperation
  but does not invalidate the signed Bitcoin transaction.
- **Token inflation or burn**: Verify token scripts, lineage, conservation,
  and change rather than trusting basket tags or relay claims.
- **Privacy**: Each party learns the transaction graph necessary to verify the
  exchange.
- **Liveness**: Either party can stop cooperating. Atomic safety does not
  guarantee completion.

## Conformance cases

A conforming implementation MUST test at least:

1. one 1Sat Ordinal NFT exchanged for a BSV-21 amount with exact token change;
2. two 1Sat Ordinal NFTs exchanged with correct satoshi tracing;
3. two BSV-21 token IDs exchanged with independent conservation;
4. a builder-funded ordinary BSV payment;
5. builder-added inputs and change in the final candidate;
6. a BSV-only builder that has no separate asset authorization;
7. rejection of an ordinary BSV leg proposed by the non-builder;
8. wrong recipient, amount, token ID, ordinal ordering, or fee output;
9. changes to version, lock time, input sequences, or other committed fields
   after review or signing;
10. rejection of every sighash byte other than `0x41`, including otherwise
    valid signatures with weaker commitments; and
11. a submission timeout followed by discovery of either the expected
   transaction or a conflicting spend.
