# BRC-178: Collaborative Atomic Exchange for BRC-100 Wallets

Open Protocol Labs ([info@opl.dev](mailto:info@opl.dev))

## Abstract

This document defines a two-party atomic exchange profile for applications and
wallets that implement [BRC-100](../wallet/0100.md). The parties contribute
UTXOs to one transaction, independently verify the final funded transaction,
and sign only their own inputs with `SIGHASH_ALL | SIGHASH_FORKID`. The exchange
either moves every agreed asset in that transaction or moves none of them.

The base profile supports ordinary BSV. It also defines required profiles for
non-fungible tokens (NFTs) represented as 1Sat Ordinals and for BSV-21
fungible tokens by composing the existing 1Sat, BSV-21, basket, proof, and
BRC-100 standards. It does not define a new token, overlay, wallet interface,
marketplace lock, or transport.

## Motivation

[BRC-79](./0079.md) gives the conceptual foundation for exchanging tokens on
UTXO-based overlay networks. Its accepting party first uses `SIGHASH_SINGLE`
and the offering party completes the transaction with `SIGHASH_ALL`. It does
not define how two current BRC-100 wallets construct, review, sign, recover,
and internalize a fully funded exchange containing 1Sat Ordinals or BSV-21
tokens.

Applications have consequently built incompatible coordination messages and
wallet-specific signing paths. This document defines the smallest common
transaction and authorization contract needed for interoperable BRC-100
implementations. Presence, discovery, chat, order books, user interface,
storage, and coordinator deployment remain application concerns.

## Relationship to BRC-79

This BRC extends rather than amends BRC-79.

BRC-79's asymmetric signing sequence remains a valid exchange construction for
implementations that deliberately use it. This profile instead requires every
contributor to review the final funded transaction and use
`SIGHASH_ALL | SIGHASH_FORKID`. This has three consequences:

1. wallet-added funding inputs and change are fixed before either party signs;
2. every signature commits to every input and output; and
3. changing any asset recipient, token amount, fee output, input, version,
   sequence, or lock time requires fresh authorization from both parties.

Implementations MUST identify which profile they use and MUST NOT combine
signatures from the two profiles.

## Terminology

- **Party**: One of exactly two asset owners in an exchange.
- **Builder**: The party whose BRC-100 wallet constructs and funds the final
  signable action. The builder pays mining fees.
- **Contribution**: The asset inputs and receiver-controlled destinations a
  party supplies for one exchange attempt.
- **Attempt**: One immutable transaction-construction attempt. Rebuilding the
  transaction creates a new attempt and requires new signatures.
- **Final template**: The transaction returned by the builder wallet after it
  has added funding and change, with every unlocking script treated as empty
  for the template commitment.
- **Coordinator**: An optional relay or state service. It has no wallet
  authority and its state is not evidence that an exchange settled.
- **Acceptance evidence**: Evidence that the exact transaction was accepted by
  the relevant network and, for overlay assets, admitted by the relevant
  overlay.

The key words `MUST`, `MUST NOT`, `SHOULD`, and `MAY` are normative.

## Scope and requirements

Version 1 of this profile:

- has exactly two parties;
- uses one Bitcoin transaction for all exchange legs;
- requires one fixed builder for an attempt;
- requires `SIGHASH_ALL | SIGHASH_FORKID` (`0x41`) on every contributed asset
  input;
- supports BSV, 1Sat Ordinal NFTs, and BSV-21 value outputs;
- permits only plain owner-controlled inputs for which the wallet can produce
  and locally verify the unlocking script; and
- uses BRC-100 for wallet construction, signatures, cancellation, and receipt
  internalization.

Cosigner-gated instruments, minting authority, token deployment, token minting,
burns, more than two parties, and script types a wallet cannot independently
validate are out of scope. An implementation MUST fail closed when it encounters
one of them.

## Authenticated communication

Exchange messages SHOULD travel over a mutually authenticated BRC-103 channel,
using a transport such as BRC-104. When an application persists commands in an
untrusted relay or needs signatures that survive a session, it SHOULD sign the
exact command bytes with BRC-77.

An implementation MUST NOT treat a display name, cursor, room identifier,
coordinator account, or unsigned public key as a party identity. It MAY display
BRC-52 certificate fields disclosed through BRC-103, but certificate display is
not transaction authorization.

The transport MUST bind every message to:

- a fresh exchange identifier;
- a positive attempt number;
- both party identity keys;
- the sender and intended recipient;
- the Bitcoin network;
- an expiry; and
- a one-use nonce or an authenticated monotonically increasing sequence.

Reusing the same binding with different bytes MUST be rejected. Receiving the
same authenticated bytes again MUST be idempotent.

## Locked exchange intent

Before transaction construction, both parties MUST authenticate the same locked
intent. The intent contains:

```json
{
  "profile": "brc-178",
  "version": 1,
  "network": "main",
  "exchangeId": "application-chosen unique value",
  "attempt": 1,
  "parties": ["compressed identity key A", "compressed identity key B"],
  "builder": "compressed identity key A",
  "expiresAt": 0,
  "legs": []
}
```

Each leg names its owner, receiver, asset profile, and quantity or outpoint. A
party MUST NOT occur as both owner and receiver of the same leg. Duplicate legs
for the same non-fungible outpoint are invalid.

If the application needs a durable intent digest, it MUST canonicalize the
object with RFC 8785 JSON Canonicalization Scheme, encode it as UTF-8, and apply
SHA-256. Numeric asset quantities MUST be represented as base-10 strings so
cross-language number conversion cannot alter them. Unknown critical fields
MUST cause rejection.

An intent authenticates what the parties discussed. It does not prove ownership
or authorize a spend. Each wallet independently derives the actual effects from
the final transaction before signing.

## Asset legs

### BSV

A BSV leg contains a positive integer `satoshis` quantity and a destination
controlled by the receiver. In version 1, a party that pays BSV MUST be the
builder because the BRC-100 wallet owns ordinary funding selection and change.
The builder wallet MUST show the BSV payment separately from mining fees and
change.

### 1Sat Ordinals (NFTs)

A 1Sat leg names the current tip outpoint and SHOULD name its claimed origin.
The owner MUST prove and recheck that:

1. the tip exists, is unspent, and is controlled by the owner;
2. the tip is a one-satoshi output;
3. the tip-to-origin relationship is valid under BRC-159, preferably with a
   BRC-150 remittance; and
4. the final transaction's satoshi ordering moves that exact satoshi into the
   receiver's named one-satoshi output.

The receiving output and its remittance MUST follow the BRC-147 `1sat` basket
profile. An implementation MUST trace the final funded transaction and MUST NOT
assume that requested input or output indexes were preserved by the builder
wallet.

### BSV-21

A BSV-21 leg names a BRC-161/BRC-162 token id and a positive atomic amount. A
symbol, icon, decimal precision, or display name is not an asset identifier.

At construction and again immediately before signing, the owner MUST establish
that every selected tip:

1. is an unspent BSV-21 value output of the exact token id;
2. is valid under BRC-161 or BRC-162;
3. has sufficient lineage evidence under BRC-176 or an equivalently verified
   live overlay response; and
4. uses a supported owner-controlled locking script.

For every token id in the exchange, the final transaction MUST satisfy:

```text
sum(valid selected value inputs)
  = sum(receiver value outputs) + sum(owner change outputs)
```

All amounts are unsigned 64-bit integers. Change is mandatory when selected
inputs exceed the locked amount. Deploy, mint, authority, and burn outputs are
forbidden. Implicit burn is forbidden. Quantities from different token ids MUST
never be netted together.

Receiving and change outputs MUST follow the BRC-163 `bsv21` basket profile.
When the target overlay requires an admission or indexing fee, the application
MUST resolve that policy before signing and include the exact fee outputs in the
final template. This BRC does not standardize a fee service, fee address, or
fee schedule.

## Destination control

Every receiver MUST approve or derive its own destination locking scripts. A
raw script supplied only by the other party or coordinator is insufficient.

For BRC-42-derived locks, the destination description SHOULD identify the
BRC-43 protocol ID, key ID, and counterparty needed by the receiver to recognize
and later spend the output. These values travel in the BRC-147 or BRC-163
remittance where applicable. Private keys and wallet action references MUST
never leave the wallet process.

## Transaction construction

The builder requests a BRC-100 signable action containing every agreed asset
input and output. The request MUST use:

```json
{
  "options": {
    "signAndProcess": false,
    "randomizeOutputs": false
  }
}
```

Asset source transactions and proofs are supplied through `inputBEEF`. Inputs
whose unlocking scripts will be supplied later use the BRC-100
`unlockingScriptLength` mechanism. The builder wallet MAY add ordinary funding
inputs and change.

The BRC-100 action reference is local capability material. The builder MUST NOT
send it to the other party or coordinator. If the attempt ends before an asset
signature is released, the builder SHOULD call `abortAction` with that
reference.

After `createAction`, both parties MUST reconstruct and validate the final
transaction from the returned Atomic BEEF. The final template commitment is:

```text
templateHash = SHA256(raw transaction serialization with every input script empty)
```

The BEEF container itself MUST NOT be hashed as the template commitment because
equivalent BEEF packages can encode proof material differently.

## Required review before signing

Each party MUST reject the final template unless all of these checks pass:

1. network, exchange identifier, attempt, parties, builder, and expiry match;
2. every agreed asset input appears exactly once and no unagreed asset input is
   attributed to that party;
3. every receiver-controlled destination matches the receiver's approval;
4. every BSV amount and fee effect matches the locked intent;
5. every 1Sat input maps by satoshi ordering to its exact receiver output;
6. BSV-21 ids, validity, quantities, change, and any required overlay fees are
   correct;
7. transaction version, input sequences, output order, output scripts, output
   satoshis, and lock time are acceptable; and
8. the wallet's own permission policy authorizes the displayed effects.

Coordinator metadata and pre-build indexes are hints only. The transaction is
authoritative.

## Signing and finalization

For each input it owns, a party computes the BSV fork-ID signature preimage for
the final template and asks its BRC-100 wallet to create the signature with the
input's local BRC-42/BRC-43 derivation information. The resulting unlocking
script MUST append sighash byte `0x41` and MUST pass local Bitcoin Script
verification against the source output before it is released.

A party MUST NOT release a signature made with `SIGHASH_NONE`,
`SIGHASH_SINGLE`, or `SIGHASH_ANYONECANPAY` under this profile. It MUST sign
exactly its owned contributed inputs and no others.

The builder MUST verify every received unlocking script against the same final
template. It then supplies those scripts to BRC-100 `signAction` for the retained
action reference. `signAction` signs the builder wallet's funding inputs and
returns or broadcasts the completed transaction.

Any transaction change, stale input, changed overlay policy, expired intent, or
failed verification invalidates the attempt. A replacement transaction MUST use
a higher attempt number and fresh authorization from both parties. An
implementation MUST NOT patch an already authorized template.

## Submission, evidence, and internalization

The Bitcoin transaction id is derived from the exact completed transaction.
Retries MUST submit the same bytes and therefore the same transaction id. A
coordinator lease MAY reduce duplicate submissions, but it is not a security
boundary and is not evidence of acceptance.

Applications MUST distinguish at least these outcomes:

- **authorized**: all required signatures exist;
- **submitted**: submission was attempted;
- **accepted**: the exact transaction has positive network evidence;
- **overlay pending**: the transaction exists but a required overlay has not
  admitted its outputs;
- **settled**: required network and overlay evidence exists; and
- **outcome unknown**: a submission may have succeeded, but evidence is
  inconclusive.

A timeout MUST NOT be reported as failure or cancellation. While the outcome is
unknown, the implementation checks the expected transaction id and every
committed input. Discovery of the exact transaction resumes verification.
Discovery of a different transaction spending a committed input marks the
attempt conflicted.

After settlement evidence is available, each wallet SHOULD call BRC-100
`internalizeAction` for outputs it controls:

- 1Sat Ordinals use BRC-147 basket insertion into `1sat`;
- BSV-21 uses BRC-163 basket insertion into `bsv21`; and
- ordinary BSV uses the applicable BRC-100 payment remittance.

Internalization MUST be idempotent. A local internalization failure does not
reverse or invalidate the on-chain exchange.

## Local reservations

A wallet or application SHOULD avoid selecting the same asset input for two
concurrent attempts. Such a reservation is local bookkeeping, not a global
lock and not an interoperable wire object. A reservation expiry does not prove
that a released signature was unused.

Once any asset unlocking script has left its wallet process, cancellation can
only stop cooperation; it cannot guarantee that the transaction will not be
broadcast. The application MUST retain enough information to determine the
outcome.

## Security considerations

- **Atomicity**: All legs are inputs and outputs of one transaction. A partial
  asset transfer cannot be mined.
- **Coordinator compromise**: A coordinator can delay, omit, or replay messages,
  but exact-template signatures prevent it from changing transaction effects.
- **Signature replay**: A `0x41` signature is useful only for the same complete
  transaction. Attempt and expiry bindings prevent an application from
  presenting stale authorization as current, although an already released
  valid transaction signature cannot be revoked.
- **Stale or double-spent inputs**: Recheck immediately before signing. A race
  can make the whole transaction lose, but cannot settle only one leg.
- **Token inflation or burn**: Parse scripts and verify lineage; do not trust
  basket tags, custom instructions, symbols, or coordinator claims.
- **Destination substitution**: Require receiver-controlled destination
  derivation and exact final-template review.
- **Fee substitution**: Treat mining fees, BSV payments, application fees, and
  overlay fees as separate effects in wallet review.
- **Privacy**: The parties learn the inputs and outputs required to verify the
  exchange. This profile does not hide the transaction graph from them.
- **Liveness**: Either party or the builder can stop cooperating. Atomic safety
  does not guarantee completion.

## Conformance cases

A conforming implementation MUST test at least:

1. one 1Sat Ordinal NFT exchanged for an exact BSV-21 quantity with BSV-21
   change;
2. two different BSV-21 token ids exchanged with independent conservation;
3. a builder-funded BSV leg;
4. reordered funding inputs and change outputs in the final wallet result;
5. wrong recipient, amount, token id, ordinal sat ordering, or fee output;
6. missing BRC-176 lineage, spent tips, and non-plain locking scripts;
7. every prohibited sighash flag;
8. duplicate, expired, and conflicting attempts;
9. submission timeout followed by discovery of the exact transaction;
10. submission timeout followed by a conflicting spender; and
11. delayed overlay admission and idempotent internalization.
