# BRC-178: Collaborative Atomic Exchange for BRC-100 Wallets

Luke Rohenaz ([luke@opl.dev](mailto:luke@opl.dev)) — Open Protocol Labs

**Status:** Draft. Independent wallet interoperability has not yet been demonstrated.

## Abstract

This document defines a collaborative exchange profile for two BRC-100
wallets. It specifies revisable trade terms, independent ready states, and
the construction, review, and signing of one Bitcoin transaction exchanging
BSV, 1Sat Ordinal NFTs, BSV-21 fungible tokens, or a mixture.

The parties first agree on trade terms, then resolve those terms to concrete
inputs and receiver-controlled outputs. One wallet constructs and funds a
final candidate transaction. Each party independently verifies that candidate
and signs only the inputs it owns with `SIGHASH_ALL | SIGHASH_FORKID`. The
transaction spends all included inputs and creates all included outputs
atomically. Asset-level correctness additionally depends on verified
provenance, token validity, and the rules of each asset profile. Bitcoin
acceptance does not guarantee admission by an overlay service.

Bitcoin transaction signatures authorize the spends. This profile does not
require a separately signed offer or application-level commitment, and it
does not prescribe a coordinator or transport protocol.

## Motivation

[BRC-79](./0079.md) describes a token exchange in which one party first uses
`SIGHASH_SINGLE` and the other completes the transaction with
`SIGHASH_ALL`. That construction remains valid.

Current BRC-100 wallets can instead wait until every concrete input, output,
fee, and change output is fixed, then have both parties review the final funded
transaction and use `SIGHASH_ALL | SIGHASH_FORKID`. This profile specifies
the construction and verification requirements for 1Sat Ordinals and BSV-21.

A common application is a video-game-style trade window: either participant
adds or removes items, inspects the other side, and toggles readiness. An edit
invalidates earlier confirmations. Only readiness from both parties for the
same terms starts an exchange attempt. This avoids treating a click on stale
terms as approval of a different trade.

This proposal composes existing mechanisms into one behavioral profile. It
introduces neither atomic exchange nor a new signature scheme. Its contribution
is the combination of revisable readiness, a fixed transaction before signing,
BRC-100 action handling, and asset-specific verification requirements.

## Scope

Version 1:

- has exactly two parties;
- settles every exchange leg in one Bitcoin transaction;
- uses one BRC-100 wallet as the transaction builder and mining-fee payer;
- supports ordinary BSV, 1Sat Ordinal NFTs, and BSV-21 value outputs;
- permits ordinary BSV to be contributed by the builder only;
- requires each party to validate all asset inputs and sign only its own; and
- uses existing BRC-100, 1Sat, and BSV-21 mechanisms.

This is a same-chain exchange and readiness profile. It defines observable
state transitions and verification requirements, not a complete application.
It does not define cross-chain swaps, standing orders signed in advance,
escrow, a new token, script template, basket, or wallet method. Discovery,
chat, visual layout, durable storage, and reservation mechanisms are outside
scope. A transport binding must carry the logical information specified below;
this document does not prescribe its serialization or network endpoints.

Two applications need a common transport binding as well as this profile to
communicate. Two wallets may use different internal storage, key derivation,
and user interfaces while following the same exchange rules.

## Relationship to BRC-79

BRC-79 and this profile use different signing sequences.

BRC-79 permits the accepting party to commit to one output first with
`SIGHASH_SINGLE` while all transaction inputs are already fixed. Historical
1Sat marketplace flows also use `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` when a
seller must sign before a buyer adds funding inputs and outputs. In this
profile, no input is signed until the builder has produced the final funded
transaction, and every contributed input uses
`SIGHASH_ALL | SIGHASH_FORKID`.

Implementations MUST NOT combine signatures from the two profiles.

## Terminology

- **Builder**: The party whose BRC-100 wallet constructs and funds the
  candidate transaction.
- **Terms confirmation**: A user-interface decision to accept the proposed
  trade. It is not a Bitcoin signature and does not freeze a transaction.
- **Contribution**: The concrete asset outpoints, receiver-controlled output
  scripts, token change, and fresh validation evidence supplied by one party.
- **Candidate transaction**: The complete transaction structure after the
  builder wallet has added funding inputs and change, but before all unlocking
  scripts are present.
- **Asset input**: A 1Sat Ordinal or BSV-21 input contributed by either party.
- **Receipt output**: An output controlled by the party receiving an asset.

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**,
**SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **NOT RECOMMENDED**, **MAY**, and
**OPTIONAL** in this document are to be interpreted as described in BCP 14
([RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and
[RFC 8174](https://www.rfc-editor.org/rfc/rfc8174)) when, and only when, they
appear in all capitals, as shown here.

## Specification

### Negotiation and readiness

A trade session identifies exactly two parties and one current **terms
revision**. Terms identify each party's offered assets and amounts, the
intended recipients, the builder selection rule, and any agreed fee limits.
An empty side MAY be displayed while editing; an application MAY reject an
empty or otherwise unsupported trade when readiness is requested.

Each party has a ready state for the current revision, initially false.
Readiness confirms the displayed terms. It is not a Bitcoin signature, proof
of asset availability, or a promise that settlement will succeed.

While the session is negotiating:

1. Either party MUST be able to add, remove, or change its offered items.
   An accepted terms change MUST create a new revision and clear **both**
   ready states. This applies even if the displayed terms return to an earlier
   value; a revision MUST NOT be reused within the session.
2. Each party MUST be able to set its own ready state to true independently.
   The request MUST identify the exact revision that party reviewed. A request
   for an older revision MUST NOT confirm the current revision.
3. A ready party MUST be able to withdraw readiness, for example by clicking
   the same Confirm button again. Withdrawal clears that party's ready state;
   it need not clear the other party's readiness for unchanged terms.
4. There MUST be no protocol limit on repeated confirm/withdraw/edit cycles.
   Implementations MAY rate-limit traffic, but MUST NOT turn a rejected or
   delayed operation into confirmation or signing.
5. Neither party may set the other party's ready state. Applications MUST
   authenticate the actor responsible for every terms or readiness operation.

A Confirm button may toggle local intent, but the logical operation sent to
the session MUST set an explicit desired state, true or false. Retrying a
request MUST NOT toggle it again. Operations MUST be bound to the session,
terms revision, and actor, and carry an operation identity and an ordering
mechanism sufficient to reject duplicates and superseded actor operations.
For example, a delayed confirm must not override a newer withdrawal.

**Both ready** means both ready flags are true for the same current revision
in the accepted session state. It does not mean two clicks occurred at the
same wall-clock instant. The application MUST serialize terms changes,
readiness updates, and the transition to an attempt under one consistent
ordering rule, such as a conditional update of authoritative session state.
A peer-to-peer implementation MUST establish equivalent agreement on that
transition before constructing or signing. A disconnected or partitioned
session MUST NOT independently start competing attempts.

When both flags are true, one indivisible transition MUST freeze that revision
and start at most one attempt. The transition MUST check that the session is
still negotiating, the revision is current, and both ready flags still apply.
If a withdrawal or edit is ordered first, the transition MUST fail. If the
transition is ordered first, later editing or readiness requests MUST NOT
mutate the attempt. Requests MUST receive an outcome that distinguishes
accepted, stale, and already attempting; the interface MUST NOT display an
unacknowledged withdrawal as a completed cancellation.

| Current state | Accepted operation | Result |
| --- | --- | --- |
| Negotiating | Edit own terms | New revision; both unready |
| Negotiating | Set ready for current revision | Update only actor's flag; start one attempt if both are ready |
| Negotiating | Withdraw readiness | Actor unready; continue negotiating |
| Negotiating | Duplicate, stale, or superseded operation | No state change |
| Attempting | Edit or readiness operation | No mutation; report attempt already started |
| Attempting | Failure before any signature is released | Abort retained action, close attempt, reopen with both unready and a new revision |
| Attempting | A signature was released or submission is uncertain | Reconcile the attempt; do not reopen merely because a timer expired |
| Reconciling | Expected transaction accepted | Record acceptance and complete required overlay/receipt handling |
| Reconciling | Original candidate proven unable to settle | Close attempt; a new revision may be negotiated with both unready |

An accepted attempt starts contribution resolution and transaction review;
it does not skip wallet approval or authorize a spend by itself. A wallet MUST
NOT sign if its local user has rejected the attempt. A cancellation request
after the freeze may stop cooperation, but MUST NOT be represented as revoking
a signature already released. The interface SHOULD make the change from
reversible readiness to an attempt visible before any signature is released.

### Contribution resolution

For the frozen terms, each wallet resolves current asset outpoints, token
change, receiver-approved destinations, and validation evidence. Selecting
fungible tips or ordinary funding inputs does not itself change the terms.
Changing an offered identity, quantity, recipient, or agreed fee limit does:
the attempt MUST stop and the changed terms require a new revision with both
parties initially unready. Every receiver MUST supply or approve its own
destination scripts, including the remittance information needed to receive
and later spend the assets under the applicable basket profile.

If one side offers ordinary BSV, that side MUST be the builder. Its BRC-100
wallet selects ordinary funding inputs and creates change. Otherwise, the
parties MAY use any agreed deterministic builder selection rule. Both complete
contributions are required before construction.

A live application SHOULD use a mutually authenticated channel such as
BRC-103. Messages persisted in an untrusted relay MAY additionally use BRC-77.
The selected mechanism MUST bind actor operations to their authenticated
sender; a relay's claim of identity or readiness is insufficient. Transport
bindings must preserve the session and revision checks above. No application
message substitutes for the final transaction signature.

Parties MUST NOT sign Bitcoin inputs during negotiation or contribution
resolution. A change to a signature-committed candidate field requires fresh
review and replacement of every signature already produced. Previously
released signatures remain valid for the old candidate; see recovery below.

### Evidence and trust model

Each wallet MUST choose its own trust policy before accepting evidence. The
counterparty MUST NOT choose a trusted header source, overlay operator, or
maximum evidence age on the receiving wallet's behalf. Implementations MUST
distinguish three different claims:

| Claim | Required verification |
| --- | --- |
| Source transaction validity | Verify source bodies and supporting proofs under the applicable BEEF rules against locally trusted chain information |
| Asset provenance or token lineage | Verify BRC-150/159 provenance or BRC-176 token lineage for the exact offered outpoints; alternatively use a locally trusted asset validator as described below |
| Current availability | Check current spent status using a locally trusted source; a historical proof alone does not prove that an output remains unspent |

A wallet that relies on an overlay's asset-validation result MUST explicitly
trust that operator for that claim, authenticate the response, and bind it to
the chain, exact outpoints, token IDs and amounts where applicable, and the
validation rules used. This is delegated validation, not an offline proof.
A counterparty-supplied `active`, `unspent`, or `verified` flag is insufficient.
Missing evidence, an untrusted responder, a scope mismatch, or a failed
validation MUST prevent signing.

Each wallet MUST impose a finite, non-negative maximum age for spent-status
and fee-policy observations and recheck freshness immediately before signing.
An observation records the locally established acquisition time and its source;
a counterparty timestamp MUST NOT establish freshness. Future-dated, unknown,
or stale observations MUST be rejected or refreshed. A refresh MUST preserve
the scope being checked. Different wallets MAY use different age limits and
trust sources; either wallet may refuse to proceed. Freshness reduces races;
it does not reserve an outpoint or prevent a subsequent double spend.

### Proof packaging

The candidate transaction and asset proofs have different completeness rules.
The candidate MAY use BRC-95 Atomic BEEF. An unsigned candidate is a signing
container, not evidence that its incomplete spends already validate.

BRC-176 packets MUST retain the full token-parent bodies required by that
standard, including bodies behind mined ancestors. They MUST NOT be stripped,
validated, or round-tripped as ordinary SPV-minimal Atomic BEEF. The same
byte framing does not make the two validation profiles interchangeable.
Ordinal provenance MUST likewise retain the bodies and funding information
required by BRC-150/159 for satoshi tracing.

A transport binding MUST distinguish candidate data from asset evidence and
identify the exact subject outpoints and evidence profile. It MAY carry them
as separate payloads or in a container that preserves both completeness rules.
It MUST also convey agreed terms and revision, receiver-approved scripts and
remittance data, and candidate-bound authorization results. It MUST NOT send
the builder's local action reference. This document specifies those semantic
requirements without defining a new wire encoding.

### Transaction construction

The builder MUST possess both complete contributions before asking its wallet
to construct the transaction. It MUST NOT substitute display metadata for a
concrete outpoint, locking script, token quantity, or source proof.

The builder asks its BRC-100 wallet to create the candidate transaction with:

```json
{
  "options": {
    "signAndProcess": false,
    "randomizeOutputs": false
  }
}
```

Asset source transactions and proofs are supplied through `inputBEEF`.
Inputs that will be signed later use the BRC-100
`unlockingScriptLength` mechanism. The builder wallet MAY add ordinary
funding inputs and change. If the terms contain an ordinary BSV leg, the
corresponding payment output is included in this same call; a non-builder never
appends ordinary BSV inputs after this point.

The builder sends the resulting candidate transaction and the source data
needed to validate it to the other party. Atomic BEEF is the RECOMMENDED
candidate container; asset evidence follows the separate completeness rules
above. BIP-174 PSBT is not required: a partially signed transaction format
can transport metadata and signatures, but it does not change which transaction
fields a signature commits to.

The BRC-100 action reference returned to the builder is a capability for
completing the retained wallet action. It MUST NOT be sent to the other party
or a relay. If construction ends before completion, the builder SHOULD call
`abortAction`.

### Required review

Before signing, each party MUST reconstruct the candidate transaction and
verify:

1. every asset input it agreed to contribute appears exactly once;
2. it is not being asked to sign any other input;
3. every expected receipt output has the approved script, satoshi value, asset
   identity, and asset quantity;
4. every change output belonging to it is correct;
5. ordinary BSV payments, mining fees, and overlay fees are separately
   acceptable;
6. every input is current, unspent, and valid under its asset profile; and
7. transaction version, outpoints, input sequences, output order, output
   scripts, output satoshis, and lock time are acceptable.

The candidate transaction is authoritative. Display metadata, a relay record,
an offer identifier, and pre-build input or output indexes MUST NOT override
what the wallet derives from the transaction. A review manifest or equivalent
local record MUST bind every field listed above, including version, lock time,
and every input sequence. Signing MUST fail if the candidate differs from
that reviewed record in any signature-committed field.

### 1Sat Ordinal NFT requirements

A 1Sat Ordinal input is identified by its current tip outpoint, not its image,
name, metadata, or claimed origin.

Before signing, both parties MUST verify that:

1. the tip is unspent and controlled by the contributing wallet;
2. the source output contains exactly one satoshi;
3. the tip-to-origin relationship is valid under BRC-159, preferably with a
   BRC-150 remittance; and
4. transaction satoshi ordering moves that exact satoshi into the approved
   one-satoshi receipt output.

The receipt output and remittance MUST follow the BRC-147 `1sat` basket
profile. Implementations MUST trace the final candidate transaction and MUST
NOT assume the builder preserved requested input or output indexes.

### BSV-21 requirements

A BSV-21 transfer is identified by its BRC-161 or BRC-162 token ID and an
unsigned 64-bit atomic amount. A symbol, icon, decimal precision, or display
name is not an asset identifier.

Before signing, both parties MUST establish that every selected token input:

1. is an unspent value output for the exact token ID, including an eligible
   prior deploy/mint value output as defined by BRC-161 or BRC-162;
2. is valid under BRC-161 or BRC-162;
3. has verified lineage under BRC-176 or an authenticated result from a
   locally trusted validator under the evidence policy above; and
4. uses a supported owner-controlled locking script.

For each token ID, the candidate transaction MUST satisfy:

```text
sum(valid selected value inputs)
  = sum(receiver value outputs) + sum(owner change outputs)
```

Change is mandatory when selected inputs exceed the transferred amount.
The exchange MUST NOT create deploy, mint, authority or burn operations, or
implicitly burn value. This restriction does not exclude a previously created,
valid deploy/mint value output from the selected inputs; it excludes authority
inputs and the creation of new token supply by the exchange.
Amounts from different token IDs MUST NOT be combined.

Receipt and change outputs MUST follow the BRC-163 `bsv21` basket profile.
Any overlay admission fee MUST be resolved and included in the candidate
transaction before either party signs.

### Signing and assembly

Each party signs exactly the inputs it owns against the final candidate
transaction. Every contributed asset input MUST use:

```text
SIGHASH_ALL | SIGHASH_FORKID = 0x41
```

This signature preimage commits to the transaction version, lock time, all
input outpoints and sequences, all outputs, and the source amount and script
for the input being signed. Other inputs' unlocking scripts are not part of
that preimage, so the parties can produce their signatures independently for
the same candidate transaction. `SIGHASH_ANYONECANPAY` is unnecessary and
forbidden because no party signs before all inputs are fixed.

Each wallet MUST locally verify every unlocking script it creates against the
source output before releasing it. The party returns its unlocking scripts, or
an equivalent partially signed transaction, to the builder.

The builder MUST verify every received unlocking script against the unchanged
candidate transaction and MUST reject any asset-input signature whose sighash
byte is not exactly `0x41`. Successful script execution alone does not establish
compliance with this signature policy. The builder then supplies the scripts
to BRC-100 `signAction` for the retained action reference. `signAction` signs
the builder wallet's ordinary funding inputs and returns or broadcasts the
completed transaction.
A builder that contributes only ordinary BSV has no separate asset-input
authorization to return; its spend authorization occurs when its wallet
reviews and completes `signAction`.

If any outpoint, sequence, output, script, satoshi amount, fee, version, or lock
time changes, the changed candidate MUST be reviewed and signed again.
Implementations MUST NOT transplant signatures onto a different candidate.

Signing before all outputs are fixed is outside this profile; BRC-79 provides
one such construction but still fixes all inputs before signing. A design
allowing inputs to be added after a signature is released needs a separate
profile defining its commitment and authorization rules. Neither construction
may be mixed into this profile's fixed-candidate `0x41` signing flow.

### Broadcast and receipt handling

Retries SHOULD submit the same completed transaction bytes. Applications MUST NOT
report a submission attempt or timeout as confirmed settlement.

For BSV-21, settlement requires both Bitcoin transaction acceptance and the
required overlay admission. Bitcoin acceptance does not by itself establish
overlay admission, and an overlay failure does not reverse an accepted Bitcoin
transaction. If the broadcast outcome is uncertain, an application SHOULD
query the expected transaction and contributed outpoints before constructing
a replacement. A timeout, disconnect, `abortAction`, or application expiry does
not invalidate released signatures. An unresolved attempt MUST NOT be retried
with different transaction contents merely because its local action was
aborted. Before reopening negotiation, establish that the original candidate
cannot settle, for example because a conflicting spend has been accepted
under the wallet's settlement policy. If that cannot be established, retain
an unresolved state and report the uncertainty. No cancellation transaction
or compensating trade is implicit in this profile.

Applications MUST track Bitcoin acceptance, required overlay admission, and
local receipt internalization as separate outcomes. They MUST NOT report
completed asset settlement while required overlay admission is unresolved.
A declined or failed attempt MUST NOT silently restore earlier ready flags.

After acceptance, each receiving wallet SHOULD call BRC-100
`internalizeAction`:

- 1Sat Ordinal NFTs use BRC-147 remittance into `1sat`;
- BSV-21 uses BRC-163 remittance into `bsv21`; and
- ordinary BSV uses the applicable BRC-100 payment remittance.

Internalization MUST be idempotent. A local internalization failure does not
reverse an accepted Bitcoin transaction.

## Security considerations

- **Atomicity**: Bitcoin inputs and outputs change together. The agreed asset
  interpretation depends on valid lineage and applicable token rules; overlay
  admission is a separate outcome.
- **Transaction substitution**: `SIGHASH_ALL | SIGHASH_FORKID` prevents a
  relay or counterparty from changing inputs or outputs after signing.
- **No second authorization object**: A signed offer or JSON object is not a
  substitute for wallet review and is not required for transaction safety.
- **Coordinator compromise**: A relay can delay, omit, duplicate, or reorder
  messages, but it cannot alter the signed transaction.
- **Stale inputs**: Recheck immediately before signing. A double spend can make
  the whole transaction invalid but cannot settle only one exchange leg.
- **Signature release**: Once a valid unlocking script is shared, a user
  cannot revoke it. An application-level expiry can stop further cooperation
  but does not invalidate the signed Bitcoin transaction.
- **Token inflation or burn**: Verify token scripts, lineage, conservation,
  and change rather than trusting basket tags or relay claims.
- **Privacy**: Each party learns the transaction graph necessary to verify the
  exchange.
- **Liveness**: Either party can stop cooperating. Atomic safety does not
  guarantee completion.

## Conformance cases

The following cases illustrate the required behavior and guide implementation testing:

1. one 1Sat Ordinal NFT exchanged for a BSV-21 amount with exact token change;
2. two 1Sat Ordinal NFTs exchanged with correct satoshi tracing;
3. two BSV-21 token IDs exchanged with independent conservation;
4. a builder-funded ordinary BSV payment;
5. builder-added inputs and change in the final candidate;
6. a BSV-only builder that has no separate asset authorization;
7. rejection of an ordinary BSV leg proposed by the non-builder;
8. wrong recipient, amount, token ID, ordinal ordering, or fee output;
9. changes to version, lock time, input sequences, or other committed fields
   after review or signing;
10. rejection of every sighash byte other than `0x41`, including otherwise
    valid signatures with weaker commitments;
11. a submission timeout followed by discovery of either the expected
    transaction or a conflicting spend;
12. repeated ready/withdraw cycles by either party without starting an attempt;
13. edits clearing both ready flags, including edit-away-and-back;
14. stale, duplicated, and reordered readiness operations, including a delayed
    confirm arriving after a withdrawal;
15. concurrent final confirmation, edit, and withdrawal, with only the ordered
    winner taking effect and at most one attempt for a frozen revision;
16. failure before signature release reopening with both unready, and failure
    after signature release preserving an unresolved attempt;
17. rejection of untrusted, stale, future-dated, or wrongly scoped evidence;
18. preservation of required token-parent and ordinal-provenance bodies during
    transport; and
19. Bitcoin acceptance with unresolved overlay admission or failed local
    internalization, without falsely reporting complete settlement.

## Worked examples and portable vectors

The [portable vectors](./media/0178-exchange-vectors.json) contain twelve logical
readiness traces and two synthetic, fully signed transaction examples: an
ordinal-for-BSV exchange and an ordinal-for-BSV21 exchange with token change.
State labels and event field names in the fixture are test notation, not a mandated
wire format. The transaction fixtures provide raw source transactions,
locking and unlocking scripts, input/output ordering, fees, satoshi positions,
and expected rejection cases. Public fixture keys MUST NOT be used for funds.

The transaction fixtures test construction, tracing, and signature verification.
Their source transactions are synthetic: they are not mined proofs, do not
establish current unspent status, and MUST NOT pass a production provenance
validator. Actual exchanges require valid BRC-150/159 and BRC-176 evidence under the
verification rules above; these synthetic examples do not establish it.

For example, Alice offers ordinal N and Bob offers 100 satoshis. Alice confirms
revision 1, then withdraws. Bob confirms; no attempt starts because Alice is
unready. Alice changes N to M: revision 2 starts with both unready. A delayed
confirmation for revision 1 is rejected. Both confirm revision 2, which freezes
once and starts construction. Further clicks cannot change that attempt.

In the ordinal-for-BSV transaction example, Alice's one-satoshi input comes first, followed by
Bob's 1,000-satoshi funding input. Outputs are one satoshi to Bob, 100 satoshis
to Alice, and 890 satoshis of Bob's change. The fee is 10 satoshis. The ordinal
occupies input position zero and output position zero. Moving Bob's funding
input ahead of Alice's input without adjusting the outputs loses the required
ordinal path and MUST be rejected.

  [regression tests](https://github.com/b-open-io/1sat-sdk/blob/ef0f83b0c3e471c40953ef94b33c8f9bf5de49e9/packages/actions/test/settlement.test.ts)

persistence and real asset verification required above; synthetic fixtures do
not substitute for those operations.
