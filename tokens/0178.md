# BRC-178: Collaborative Atomic Exchange for BRC-100 Wallets

Open Protocol Labs ([info@opl.dev](mailto:info@opl.dev))

## Abstract

This document defines how two BRC-100 wallets collaboratively construct,
review, and sign one Bitcoin transaction that exchanges BSV, 1Sat Ordinal
NFTs, or BSV-21 fungible tokens.

The parties negotiate a candidate transaction, independently verify its exact
inputs and outputs, and sign only the inputs they own with
`SIGHASH_ALL | SIGHASH_FORKID`. The transaction moves every agreed asset or
none of them.

The Bitcoin transaction signatures are the only spend authorization. This
profile does not require a separately signed offer, intent object, JSON
commitment, coordinator protocol, or transport.

## Motivation

[BRC-79](./0079.md) describes a token exchange in which one party first uses
`SIGHASH_SINGLE` and the other completes the transaction with
`SIGHASH_ALL`. That construction remains valid.

Current BRC-100 wallets can also exchange assets by having both parties review
the final funded transaction and use `SIGHASH_ALL | SIGHASH_FORKID`. This
profile specifies that simpler symmetric construction and the checks needed
for 1Sat Ordinals and BSV-21.

## Scope

Version 1:

- has exactly two parties;
- settles every exchange leg in one Bitcoin transaction;
- uses one BRC-100 wallet as the transaction builder and mining-fee payer;
- supports ordinary BSV, 1Sat Ordinal NFTs, and BSV-21 value outputs;
- supports only inputs each wallet can independently validate and sign; and
- uses existing BRC-100, 1Sat, and BSV-21 mechanisms.

This profile does not define presence, discovery, chat, order books, offer
storage, reservations, user interface, or a relay service. It does not define
a new token, overlay, script template, basket, wallet method, or message
format.

## Relationship to BRC-79

BRC-79 and this profile use different signing sequences.

BRC-79 permits the accepting party to sign a limited output first with
`SIGHASH_SINGLE`. In this profile, both parties sign only after the builder
has produced the final funded transaction, and every contributed asset input
uses `SIGHASH_ALL | SIGHASH_FORKID`.

Implementations MUST NOT combine signatures from the two profiles.

## Terminology

- **Builder**: The party whose BRC-100 wallet constructs and funds the
  candidate transaction.
- **Candidate transaction**: The complete transaction structure after the
  builder wallet has added funding inputs and change, but before all unlocking
  scripts are present.
- **Asset input**: A 1Sat Ordinal or BSV-21 input contributed by either party.
- **Receipt output**: An output controlled by the party receiving an asset.

The key words `MUST`, `MUST NOT`, `SHOULD`, and `MAY` are normative.

## Negotiation

The parties exchange proposed asset inputs, receipt outputs, and revisions of
the candidate transaction. Either party may reject a proposal or return a
revised proposal.

This profile does not prescribe a negotiation payload. A live application
SHOULD use a mutually authenticated channel such as BRC-103. An application
that persists messages in an untrusted relay MAY protect those messages with
BRC-77. Such message authentication prevents impersonation or message
tampering; it is not transaction authorization and is not required by this
profile.

No party signs a Bitcoin input until it has received and verified the final
candidate transaction. Changing the transaction after a signature is produced
requires the affected parties to review and sign the changed transaction
again.

## Transaction construction

The parties first identify the asset inputs and receiver-controlled outputs
needed for the exchange. Every receiver MUST derive or approve its own
destination locking scripts.

The builder asks its BRC-100 wallet to create the candidate transaction with:

```json
{
  "options": {
    "signAndProcess": false,
    "randomizeOutputs": false
  }
}
```

Asset source transactions and proofs are supplied through `inputBEEF`.
Inputs that will be signed later use the BRC-100
`unlockingScriptLength` mechanism. The builder wallet MAY add ordinary
funding inputs and change.

The builder sends the resulting candidate transaction and the source data
needed to validate it to the other party. Atomic BEEF is the RECOMMENDED
container.

The BRC-100 action reference returned to the builder is local capability
material. It MUST NOT be sent to the other party or a relay. If construction
ends before completion, the builder SHOULD call `abortAction`.

## Required review

Before signing, each party MUST reconstruct the candidate transaction and
verify:

1. every asset input it agreed to contribute appears exactly once;
2. it is not being asked to sign any other input;
3. every expected receipt output has the approved script, satoshi value, asset
   identity, and asset quantity;
4. every change output belonging to it is correct;
5. ordinary BSV payments, mining fees, and overlay fees are separately
   acceptable;
6. every input is current, unspent, and valid under its asset profile; and
7. transaction version, outpoints, input sequences, output order, output
   scripts, output satoshis, and lock time are acceptable.

The candidate transaction is authoritative. Display metadata, a relay record,
an offer identifier, and pre-build input or output indexes MUST NOT override
what the wallet derives from the transaction.

## 1Sat Ordinal NFT requirements

A 1Sat Ordinal input is identified by its current tip outpoint, not its image,
name, metadata, or claimed origin.

Before signing, its owner MUST verify that:

1. the tip is unspent and controlled by that wallet;
2. the source output contains exactly one satoshi;
3. the tip-to-origin relationship is valid under BRC-159, preferably with a
   BRC-150 remittance; and
4. transaction satoshi ordering moves that exact satoshi into the approved
   one-satoshi receipt output.

The receipt output and remittance MUST follow the BRC-147 `1sat` basket
profile. Implementations MUST trace the final candidate transaction and MUST
NOT assume the builder preserved requested input or output indexes.

## BSV-21 requirements

A BSV-21 transfer is identified by its BRC-161 or BRC-162 token id and an
unsigned 64-bit atomic amount. A symbol, icon, decimal precision, or display
name is not an asset identifier.

Before signing, the owner MUST establish that every selected token input:

1. is an unspent transfer output for the exact token id;
2. is valid under BRC-161 or BRC-162;
3. has sufficient lineage evidence under BRC-176 or an equivalently verified
   live overlay response; and
4. uses a supported owner-controlled locking script.

For each token id, the candidate transaction MUST satisfy:

```text
sum(valid selected value inputs)
  = sum(receiver value outputs) + sum(owner change outputs)
```

Change is mandatory when selected inputs exceed the transferred amount.
Deploy, mint, authority, burn, and implicit-burn constructions are forbidden.
Amounts from different token ids MUST NOT be combined.

Receipt and change outputs MUST follow the BRC-163 `bsv21` basket profile.
Any overlay admission fee MUST be resolved and included in the candidate
transaction before either party signs.

## Signing and assembly

Each party signs exactly the asset inputs it owns against the final candidate
transaction. Every contributed asset input MUST use:

```text
SIGHASH_ALL | SIGHASH_FORKID = 0x41
```

The standard Bitcoin signature preimage commits to all transaction outpoints,
input sequences, and outputs. Other inputs' unlocking scripts are not part of
that preimage, so the parties can produce their signatures independently for
the same candidate transaction.

Each wallet MUST locally verify every unlocking script it creates against the
source output before releasing it. The party returns its unlocking scripts, or
an equivalent partially signed transaction, to the builder.

The builder MUST verify every received unlocking script against the unchanged
candidate transaction. It then supplies the scripts to BRC-100 `signAction`
for the retained action reference. `signAction` signs the builder wallet's
funding inputs and returns or broadcasts the completed transaction.

If any outpoint, sequence, output, script, satoshi amount, fee, version, or lock
time changes, the changed candidate MUST be reviewed and signed again.
Implementations MUST NOT transplant signatures onto a different candidate.

## Broadcast and receipt handling

Retries SHOULD submit the same completed transaction bytes. Applications MUST
not report a submission attempt or timeout as confirmed settlement.

For BSV-21, settlement requires both Bitcoin transaction acceptance and the
required overlay admission. If the broadcast outcome is uncertain, an
application SHOULD query the expected transaction and contributed outpoints
before constructing a replacement.

After acceptance, each receiving wallet SHOULD call BRC-100
`internalizeAction`:

- 1Sat Ordinal NFTs use BRC-147 remittance into `1sat`;
- BSV-21 uses BRC-163 remittance into `bsv21`; and
- ordinary BSV uses the applicable BRC-100 payment remittance.

Internalization MUST be idempotent. A local internalization failure does not
reverse an accepted Bitcoin transaction.

## Security considerations

- **Atomicity**: All exchange legs occur in one transaction.
- **Transaction substitution**: `SIGHASH_ALL | SIGHASH_FORKID` prevents a
  relay or counterparty from changing inputs or outputs after signing.
- **No second authorization object**: A signed offer or JSON object is not a
  substitute for wallet review and is not required for transaction safety.
- **Coordinator compromise**: A relay can delay, omit, duplicate, or reorder
  messages, but it cannot alter the signed transaction.
- **Stale inputs**: Recheck immediately before signing. A double spend can make
  the whole transaction invalid but cannot settle only one exchange leg.
- **Signature release**: Once a valid unlocking script is shared, a user
  cannot revoke it. An application-level expiry can stop further cooperation
  but does not invalidate the signed Bitcoin transaction.
- **Token inflation or burn**: Verify token scripts, lineage, conservation,
  and change rather than trusting basket tags or relay claims.
- **Privacy**: Each party learns the transaction graph necessary to verify the
  exchange.
- **Liveness**: Either party can stop cooperating. Atomic safety does not
  guarantee completion.

## Conformance cases

A conforming implementation MUST test at least:

1. one 1Sat Ordinal NFT exchanged for a BSV-21 amount with exact token change;
2. two 1Sat Ordinal NFTs exchanged with correct satoshi tracing;
3. two BSV-21 token ids exchanged with independent conservation;
4. a builder-funded ordinary BSV payment;
5. builder-added inputs and change in the final candidate;
6. wrong recipient, amount, token id, ordinal ordering, or fee output;
7. a changed candidate after one party has signed;
8. every prohibited sighash flag; and
9. a submission timeout followed by discovery of either the expected
   transaction or a conflicting spend.
